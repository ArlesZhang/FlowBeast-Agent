## 一、我们现在在哪

市场反馈表明，下面四条早期创业路径**已被证伪**：

| # | 被证伪的路径 | 证伪方式 |
|---|-------------|---------|
| 1 | 静态语料壁垒 | 语料产出为 0；且检索到的东西传不进生成 |
| 2 | 低价抽取服务 | 无付费意愿，定价撑不起交付成本 |
| 3 | 特定品牌命名 | 用户不认品牌，只认结果 |
| 4 | 提示词包 | 一次性商品，无复购，无壁垒 |

**结论：** AI 2.0 时代轻资产模式已难以为继，从业者需要转向更深层的
**系统级工作流集成 + 业务结果交付**。

### 产品形态

> **FlowBeast 不卖编译器，也不卖提示词包。**

它的产品形态是 **「陪跑式」AI 短剧制作服务** —— 面向中国小型短剧团队，
**按交付成片集数收费**。

**是服务，不是 SaaS。** 免费的公开评分器是**获客入口**，不是产品本身。

### 唯一验收标准

> ### 有真实付费证据。

在客户为一集成片付过钱之前，任何功能、重构、文档都不算数。

### 优化目标

**可用 · 能落地 · 可集成 · 可交付 · 能赚钱。**

不追求完整，不追求优雅，不追求架构纯洁。
**能跑通的集成，胜过更聪明的自研。**

> 完整论证与 30 天计划见 [`commercialization_playbook.zh.md`](commercialization_playbook.zh.md)。

## 二、规则 0 —— 绝不重复造轮子

**默认假设：这件事市场上已经有人做过，而且做得比我们好。**

框架、包、模块、开源项目、Claude Skills、MCP、插件、SaaS API —— 这个项目需要的东西，
绝大多数已经存在、由别人维护、比我们一天写出来的更成熟。

稀缺资源**不是代码**，而是**集成 + 调度 + 商业交付**。
自己重写一个已有的轮子，花掉的正是唯一拿不回来的资源。

### 默认顺序

1. **先搜** —— GitHub / PyPI / npm / MCP registry / Skills 生态，并说明找到了什么
2. **集成** —— 当作依赖直接用（最好结果：我们自己零行代码）
3. **借鉴** —— 移植成熟的设计或算法，注明出处并核对 License
4. **自研** —— 只有在 1–3 确实失败后，并且必须说明**为什么失败**

### 硬性约束

- **库里有的，绝不手写。** 不手搓分词、重试逻辑、TTS 对齐、字幕排版、鉴权、队列、调度、向量检索。
- **优先选平庸、流行、有人维护的方案**，哪怕自己调的版本略好一点 —— 维护成本活得比调优收益久。
- **采用前核对 License。** MIT / Apache-2.0 / BSD 可用；商用链路里的 GPL/AGPL 必须先上报。
- **复制进仓库的代码会腐烂。** 优先真依赖，而不是把文件拷进 repo。
- **工具差一点点时，扩展它**（插件 / 配置 / 包装 / 提 PR），而不是 fork 出一套自己的平行实现。

### 落地检查

- 加依赖前先 `uv pip list` 看是否已装
- 写脚本前先看机器上是不是已有 CLI 能干这件事
- 造 sub-agent 前先看现有 Claude Skill / MCP server 是否覆盖
- 设计子系统前先看 [`capability_map.md`](capability_map.md)（已把能力对上现成工具）
- **把集成选择说出来**（"用 X，因为 Y；不写 Z，因为 X 已覆盖"），让决策可被 review

### 我们只自研什么

只有**真正的业务本身**：

- 把工具串成一份可交付物的**工作流胶水**
- 通用工具不可能知道的**领域逻辑**（短剧结构、中文短剧节奏、按集交付的打包方式）

底下的基础设施、管线、格式、协议 —— 都是别人的活，且已经干完了。

## 三、跟我协作的规矩

这几条写给 AI 协作者（也写给未来的自己）：

| 规矩 | 原因 |
|---|---|
| **报告用中文，仓库产物用英文** | 我读中文快；代码和文档要能对外 |
| **同一件事失败两次就停下来** | 报告错误 + 给一条我能手动执行的命令，不要循环重试烧 token |
| **先删后建** | 删掉错的东西、或换成现成工具，通常才是正解。不要在已证伪的方向上继续跑 |
| **不纠结不重要的 bug** | 项目没定型之前，很多问题会自动消失。判断标准：它挡住交付了吗？ |
| **先读 `goal.md`** | 当前阶段该做什么，那里写着。不要提阶段之外的工作 |
